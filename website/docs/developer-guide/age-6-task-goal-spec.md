В Bot Mode один main ведёт несколько поручений одновременно. У каждого поручения есть собственная цель, критерий готовности и сохранённое состояние. Goal отвечает за поручение между ходами, пока результат не достигнут, пользователь не отменил работу или для продолжения не возникло реальное препятствие.

## 0. Принятие поручения

Main определяет намерение в обычном ходе. «Как устроено ревью?» требует ответа. «Проведи ревью и верни замечания» требует результата, который агент принимает на себя. Поручение может завершиться в первом же ходе.

- **Из чата.** Main открывает поручение при принятии запроса, до первого действия по нему. Он фиксирует ожидаемый результат и по какому факту будет понятно, что работа выполнена.
- **Из трекера.** Main открывает поручение, когда берёт задачу в работу. Стабильный ID задачи в трекере связывает её с записью Hermes.
- **При продолжении.** Уточнение исходной задачи, повторная доставка входа и возвращение к задаче из трекера используют существующую запись. Если человек дал несколько независимых поручений одним сообщением, каждое получает собственный ID.

Main сам вызывает операцию открытия. Пользователь даёт поручение обычным языком. Операция возвращает `project_id` после сохранения записи. Этот ID используется при делегировании, назначении таймера и обработке результатов.

## 1. Хранение состояния

Поручение хранится в `state.db` профиля Hermes как запись существующего `ProjectStore` в `delegated_projects`. `ProjectStore.create()` уже создаёт запись отдельно от постановки работы исполнителю. Поэтому поручение может существовать до первого делегирования. Состояние Goal добавляется в метаданные этой записи рядом с ожиданием AGE‑6. [Создание записи и постановка работы](https://github.com/agentready-tech/hermes-agent/blob/363eedacb7a85de971c400b4fff6b67a6dfd80ac/tools/delegate_project_store.py#L109-L138)

| Данные | Что сохраняем |
|---|---|
| Идентичность | `project_id`, исходное сообщение или ссылка и ID задачи в трекере |
| Цель | Ожидаемый результат, критерии готовности и согласованные границы работы |
| Прогресс | Текущее состояние, последний подтверждённый этап и ссылки на результаты |
| Продолжение | Следующий шаг, активный исполнитель, ожидаемое событие или привязка таймера |
| Блокировка | Конкретная причина, что уже проверено и какое действие позволит продолжить |

Список открытых поручений восстанавливается из `ProjectStore`. Для 50 поручений хранятся 50 независимых записей в одном профиле. Отчёт исполнителя, вход пользователя и срабатывание таймера связываются с конкретным поручением по сохранённому ID. Следующий ход получает его состояние из базы, включая после рестарта или сжатия истории.

## 2. Goal вместо Continuation Guard с Decisions

Из пути продолжения поручений в Bot Mode убираются `continuation_guard` и связанный вызов Decisions. Из штатного `/goal` переиспользуются контракт результата, проверка после хода и запуск следующего хода. Сейчас `/goal` хранит цель по ID сессии. В этом режиме Goal работает с задачей по `project_id`. [Текущее хранение `/goal`](https://github.com/agentready-tech/hermes-agent/blob/fc83c8c88204186fc3f9cd3c26845e446e561eb7/hermes_cli/goals.py#L499-L502) · [Проверка цели после хода](https://github.com/agentready-tech/hermes-agent/blob/fc83c8c88204186fc3f9cd3c26845e446e561eb7/hermes_cli/goals.py#L1483-L1537)

После хода, который принёс новый результат, **один вызов LLM отвечает на один вопрос** — по каким из затронутых поручений достигнут финал и какой факт это подтверждает? Модели передаются критерии каждой цели и сохранённые результаты работы. Для каждого поручения она возвращает «достигнуто» с подтверждением или «открыто». Если ход затронул три поручения из пятидесяти, проверяются эти три. При ошибке проверки поручение остаётся открытым, а сохранённые результаты доступны для продолжения.

Дальнейшее действие для открытого поручения выбирает основная модель. Решение сохранить паузу или запустить следующий ход опирается на состояние работы.

| Состояние поручения | Переход |
|---|---|
| Есть доступный следующий шаг | Goal ставит новый ход main по этому `project_id`. Main выполняет шаг или делегирует его. |
| Исполнитель уже работает | Сохраняется связь с принятым запуском. Отчёт исполнителя возвращает поручение в main для проверки результата и выбора следующего шага. |
| Для следующего шага нужны новые данные | Main фиксирует ожидаемый факт и сам назначает контрольную точку. Если уже подтверждено событие, которое продолжит задачу, сохраняется эта связь. |
| Продолжение требует решения человека или доступа | Main фиксирует конкретный блокер и условие продолжения. Если нужен ответ пользователя, задаёт один предметный вопрос. |

Перед завершением хода Goal сохраняет результат и дальнейший переход. Готовый шаг остаётся доступен для запуска после сбоя. Повторный вход сверяется с уже принятым запуском, назначенным таймером или обработанным отчётом.

## 3. Ожидание и переиспользование AGE‑6

Из AGE‑6 берём точную связь `project_id` → `wait_id` → `job_id`, один повторяющийся таймер на ожидание, штатное пробуждение той же main-сессии и снятие таймера по точной привязке. Проверку действующего таймера, которую PR подключает к guard, переносим в переход Goal в ожидание. Goal сверяет, что job активен, относится к нужному поручению и у него есть будущий `next_run_at` в пределах срока ожидания. [Спецификация AGE‑6](https://github.com/agentready-tech/hermes-agent/blob/363eedacb7a85de971c400b4fff6b67a6dfd80ac/website/docs/developer-guide/age-6-external-wait-spec.md#L5-L14) · [Проверка таймера](https://github.com/agentready-tech/hermes-agent/blob/363eedacb7a85de971c400b4fff6b67a6dfd80ac/cron/wait_evidence.py#L6-L39)

Когда таймер срабатывает, cron передаёт в main ID поручения и ожидания. Main поднимает состояние задачи и проверяет ожидаемый факт, например пришёл ли ответ. Если новых данных нет, сохраняется следующий слот того же ожидания или main корректирует срок проверки. Пользователь в этот момент ничего не получает. Если данные появились, main продолжает поручение. Истечение срока ожидания возвращает задачу на оценку следующего шага. [Пробуждение в main](https://github.com/agentready-tech/hermes-agent/blob/363eedacb7a85de971c400b4fff6b67a6dfd80ac/hermes_runtime/standalone/events.py#L139-L158)

Для допустимой короткой проверки также берём существующий monitor gate. `no_change` сохраняет следующий слот без пробуждения main. Если для проверки нужен ход модели, тишина обеспечивается на уровне доставки в чат. [Границы monitor gate в AGE‑6](https://github.com/agentready-tech/hermes-agent/blob/363eedacb7a85de971c400b4fff6b67a6dfd80ac/website/docs/developer-guide/age-6-external-wait-spec.md#L12-L14)

## 4. Закрытие и доставка

Goal закрывает поручение после подтверждения его критериев. Запись сохраняет итог и доказательство результата. При закрытии или явной отмене Goal прекращает дальнейшие проверки и снимает связанный таймер. Повторный отчёт или уже поставленное пробуждение сверяются с состоянием поручения перед запуском.

Пользователь получает результат, существенное изменение или вопрос, от которого зависит продолжение. Служебные статусы Goal, срабатывания таймера и проверки без новых данных остаются внутри системы.

## 5. Критерии приёмки

1. Обычный вопрос получает ответ. Поручение из чата и взятая в работу задача из трекера открываются до первого действия. Повторный вход использует ту же запись.
2. В сценарии Васи после отчёта последнего исполнителя Goal видит незавершённый результат. При доступном следующем шаге main запускает его сам. Уточнение от пользователя для этого перехода не нужно.
3. Когда нужны новые данные, main сам назначает контрольную точку. Таймер будит то же поручение. Проверка без ответа сохраняет ожидание и оставляет чат тихим. Полученный ответ продолжает работу.
4. При десятках открытых поручений отчёт или таймер затрагивает только связанные записи. Повтор события и рестарт не создают дублей исполнителя или таймера и не теряют сохранённый следующий шаг.
5. Подтверждённый результат закрывает поручение со снятием его таймера. Реальный блокер сохраняет открытое состояние и понятное условие продолжения. Возврат к работе использует тот же `project_id`.
