# AGE-6 — План разработки обычного таймера ожидания

[Спецификация](./age-6-external-wait-spec.md) · Hermes draft PR #2 · база `codex/agentready-runtime`. Это уточнение текущего Dev, не новая стадия Spec. История D3/D5 остаётся в Git; условия для автономного опроса и общего изменения writers/restore не являются условиями этого среза.

[Жизненный цикл поручений](./age-6-task-goal-spec.md) описывает открытие и закрытие поручений в Bot Mode. Goal использует проверку таймера из T3, чтобы подтвердить переход поручения в ожидание.

## Решения

- **T1 — точное ожидание.** Только native owning main вызывает `delegate_task(action='external_wait')` для существующего проекта. `open` атомарно сохраняет `wait_id`, конечный aware deadline, критерий ответа и обе high-water отметки SQLite. `select` перепроверяет проект, поколение и срок. Повтор `open` не обновляет отметки. Неподтверждённый `return_path=event` не меняет проект или cron и не падает обратно на таймер.
- **T2 — существующий cron.** Main передаёт `project_id` и `wait_id` в `cronjob_manage(action='create')` вместе с prompt и recurring schedule. `ProjectStore` резервирует свежий ID для этого поколения, не усыновляет обычный job. Первый cron record публикуется сразу помеченным и paused под штатной строгой `.jobs.lock`. После подтверждения точной пары проект помечается `BOUND`, затем job возобновляется. Повтор той же операции использует тот же ID, не повторно выбирает job по имени. Несогласованные две стороны, конфликт или потеря привязки не разрешают замену. Native close под тем же fire fence сначала снимает право admission (`CLOSING`), затем удаляет только совпавшую запись и подтверждает `CLOSED`. Не добавлять отдельный scheduler, таблицу, очередь или переключатель.
- **T2 — узкая совместимость.** `cron/job_definition.py::import_job_definitions` переносит исходный ID, но выбрасывает поля вне `JOB_DEFINITION_FIELDS`. Поэтому связанные таймеры не импортируются как переносимые определения, в том числе без тега: выделенный `wait-…` ID никогда не становится обычным job. Полный backup/restore не изменяется. Частично восстановленная или устаревшая cron-запись не подтверждает допуск без текущего `BOUND` того же поколения. Перед эксплуатацией отдельно подтвердить совместимость writers и согласованность восстановления обеих сторон; локальный тест не подтверждает реальную проекцию профилей.
- **T3 — guard.** Условия включения, default-off, бюджет, приоритет explicit stop и исключения не меняются. Только выбранная действующая пара может предъявить repair-free доказательство `now < next_run_at < deadline`; типизированный статус и совпадение записей обязательны. Guard не чинит и не запускает job.
- **T4 — wake и подтверждение ответа.** Обычный tick или ручной fire проверяет точный текущий job и owning project до admission. Durable wake сохраняет `job_id:execution_id` и точную пару; использует имеющийся закреплённый маршрут или штатный HomeInbox при отсутствии привязки. Метаданные текстового конверта подсказывают контекст, но не авторизуют выбор: main делает `select` перед проверкой, в пределах уже принятого поручения. Старый/replayed/скопированный ответ не закрывает wait после compaction. Для `close(reason='reply')` требуется оригинальный нативный `session_admission` того же профиля и логической main выше watermark. При недостатке доказательства ответа таймер не снимается как выполненный.
- **T5 — отдельная offline-регрессия.** Допустимая штатная проверка не обходится при маршрутизации через `admit_cron`: `no_change` → следующий слот без wake, `change` → один durable wake. Инертная проверка не доказывает разрешённость реального источника. Для AGE-6 cron вообще не проверяет внешний источник. `monitor_url`, `monitor_script`, browser-only и живой источник не входят в критерии QA/Done этой задачи; запрет полей и отдельный monitor остаются как были.

## Проверки и передача

| Проверка | Доказательство |
|---|---|
| T1/T2 | Нативные open/create/retry; один точный job; staged/paused и не совпадающий профиль не допускаются; потерянный результат до resume восстанавливает тот же ID; штатный импорт сохраняет прочие записи и отклоняет связанный ID. |
| T3 | Временный managed профиль: нет timer proof до bind, есть после bind; отрицательные сроки, пауза, удаление, несовпадение и неизменный default-off/исключения проверяются отдельно. |
| T4 | Штатный локальный tick → ledger → существующий gateway или HomeInbox → обработка main того же поручения; следующая дата и дедуп одного occurrence; точное закрытие, соседний job остаётся. Инертный Telegram ingress → реальная compaction → старый replay не закрывает, новый original ID закрывает и снимает точную запись. Результат одного ingress не подтверждает другой (например, Panel steer). |
| T5 | Baseline/равный hash/change/failure/cancel, будущий слот и раздельные профили на инертной фикстуре; deny URL/script и alias до source I/O. |

Dev запускает целевой набор через `scripts/run_tests.sh` и `scripts/check` на временных home, фиксирует точный SHA и ограничения. Чужой dirty `test_scheduled_reply_e2e.py` не менять и не индексировать. После Dev отдельно идут независимое Review, QA на согласованном стенде с readback SHA/digest и явная приёмка. Никакой активации, QA, merge или deploy в текущем проходе.
