**Статус: решения D1–D5 зафиксированы оркестратором; контракт `close(reply)`/`event` сверён на `b4a7f2c8222837f7de4fda310e9feed9c3e0b9e5`.** Существующий Hermes draft PR #2, база `codex/agentready-runtime`. План дополняет [опубликованную спецификацию](./age-6-external-wait-spec.md), не изменяет её критерии. D5 блокирует **полную приёмку**, но не безопасную реализацию, описанную ниже. Данный проход — только документ.

## Цель, границы и исходные факты

В AgentReady Bot Mode имеется одна постоянная логическая main-сессия Hermes на профиль. Cron отдаёт продолжение принятого поручения в её существующий main inbox; он не создаёт, не ищет и не выбирает сессии и не использует `/new`. Job привязан к ожиданию поручения, не к channel/chat/session ID; каналы — только транспорт, история — штатный контекст. Проверка owning main lineage — проверка доступа внутри уже установленной сессии, не выбор назначения. Сохранить профильную изоляцию и штатное восстановление main. На одно timer-based ожидание приходится один штатный recurring job, не один job на профиль. Подтверждённый независимый return path не дублируется. Не добавлять таблицу, БД, очередь, реестр, worker, cron action, новый tool, интерфейс, сетевой fallback или автоматический retry. Не менять shared MCP/CLI, историю или кэшированный prompt prefix, default-off и исключения guard, обычные jobs вне opt-in и AGE‑5.

- `tools/delegate_tool.py::delegate_task/_build_dynamic_schema_overrides` и `agent/delegation_mail.py::dispatch` дают native точки расширения, но команды выбора/записи ожидания ещё нет. `tools/delegate_projects.py::_project_action` умеет читать и управлять детьми, а не устанавливать текущую работу main. `tools/delegate_project_store.py::ProjectStore._owned/get` даёт точное владение по parent lineage и profile DB; `save_workspace` сейчас читает JSON **до** write transaction, поэтому все изменяющие `workspace_json` пути нужно перевести на read–merge–write внутри одной транзакции, иначе child worktree update способен затереть ожидание.
- `tools/cronjob_tools.py::_cronjob_schema_overrides/_action_update` — native точки входа; разрешение нельзя выводить из видимости schema overlay или managed `origin`. `cron/jobs.py::_with_job/create_job/resume_job` дают штатные операции; обычные резолверы принимают имя. `cron/jobs.py::_jobs_lock` сейчас допускает деградацию до внутрипроцессного lock; это не гарантия уникальности. `tools/cronjob_tools.py::_action_run` способен запустить paused job вручную. Ни текущая блокировка в degraded-режиме, ни `paused` сами по себе не выполняют D3.
- `hermes_runtime/standalone/events.py::admit_cron` — общий managed admission до enqueue/wakeup. Сейчас передаваемая `metadata` сериализуется в текстовый envelope (`hermes_runtime/events.py`); это не доверенный ввод для автоматического выбора. `cron/jobs.py::get_job` вызывает `load_jobs`, который может чинить файл; `_peek_jobs_unlocked` не пишет, но не является готовым публичным guard API. Текущий guard (`agent/continuation_guard.py`, `agent/turn_stop_gates.py`) опционален и опирается на историю/receipts, а не на доказательство AGE‑6.
- Сверены Hermes `AGENTS.md`, `agent/`, `cron/`, `gateway/`, `tools/`, `tests/AGENTS.md`, `AgentReady/AGENTS.md` п. 6, правила Spec/Review/QA `sdlc-orchestrator` и `planning-gate`. Решение об изменении admission ограничено tagged AGE‑6 и reuse gate; исключение для обычных job или расширение допуска источников не следует из него. Перед реализацией общего участка `standalone/events.py` сверить пересечение с AGE‑5. Чужой dirty `tests/hermes_runtime/test_scheduled_reply_e2e.py` не менять, не индексировать и не считать доказательством на кандидатном SHA до передачи владельцем.

## Сценарии и критерии

**Основной сценарий — продолжение поручения, не проверка чата.** Штатный cron ставит продолжение в существующий durable main inbox (сохраняя штатный маршрут доставки), и та же логическая сессия Hermes работает с уже поступившими входящими и сохранённым состоянием. Подходящий вход, принятый **после фиксации ожидания**, может его закрыть; старый похожий ответ не засчитывается. Ни опроса канала или истории как внешнего источника, ни привязки job к channel/chat ID, ни браузера, ни URL. Это обычное плановое пробуждение, не zero-LLM quiet gate. Browser-only и quiet monitor — отдельные условные ветки опубликованной спеки, не предпосылки этого сценария; допуск не меняется.

| ID | Сценарий и наблюдаемый результат | На базе |
|---|---|---|
| S1 | Main явно открывает ожидание для принадлежащего ему проекта до cron; без таймера есть открытая запись, но нет доказательства пробуждения. Чужой/невыбранный проект не превращается в ожидание. | Не закрыт |
| S2 | Один job на пару, pre-bind job не запускается автоматически или вручную; повтор/конкуренция не создают дубль. Закрытие отнимает право проверки до удаления job. | Не закрыт |
| S2a | В логической main-сессии до открытия есть старый подходящий ответ: он не засчитывается. После открытия поступает новый подходящий вход; штатный cron wake отдаёт управление той же сессии, она обрабатывает уже принятый вход, закрывает точное ожидание и снимает таймер. Ноль запросов к любому каналу, браузеру или endpoint. | Не закрыт |
| S3 | Browser-only: тот же main и ожидание, один разрешённый источник и не более одной попытки на occurrence, интервал и конечный срок. При отсутствии ответа нет пустого отчёта; модель может работать. Просроченный, закрытый или неподтверждённый тик не открывает источник. | Только инструкции |
| S4 | Quiet: baseline не ответ; равный hash → штатный `no_change`/`[SILENT]`, следующий `next_run_at` того же job, ноль wake/LLM/доставки. Изменение → один admission в том же main; ошибка не меняет hash и не запускает fallback. | Managed gate не подтверждён; реальный источник заблокирован |
| S5 | Точный guard-proof только для выбранного ожидания, default-off и исключения неизменны. Нет доказательства → bounded nudge только на известном открытом timer-based ожидании. Legacy jobs и закрытый ввод URL/script сохраняются. | Запрет полей проверяется тестами в базе; guard-proof не закрыт |

### D1–D2: native контракт и состояние проекта

- В существующем `delegate_task` добавляется native action `external_wait`: payload `op`, точный `project_id`; для `open` — `mode` (`resume_main` или `browser_only`), `reply_criterion`, timezone-aware конечный `deadline`, `return_path` (`timer` или подтверждённый `event`). `source_ref` допустим и обязателен только при `browser_only` (точный разрешённый источник); при `resume_main` поля адреса/канала/чата не принимаются. Для `select/close` — точный `wait_id`, для `close` — причина. `open` возвращает сгенерированный runtime `wait_id`; повтор идентичного `open` для того же открытого ожидания возвращает текущую пару, не создаёт новое поколение; несовпадающий payload или закрытие в процессе — отказ. `select` только читает существующую открытую пару и привязывает её к текущему native turn; `close` инвалидирует её по точной паре. После завершённой очистки новый `open` получает новый `wait_id`. Не заводить новый project и не слать child mail.
- Runtime-авторизация: текущий owning managed main с его native agent/turn, профиль и логическая main lineage, exact `ProjectStore` ownership; модель поставляет ID как запрос выбора, не полномочие. Профильный schema overlay не авторизует вызов. На пользовательском ходу источник выбора — однозначная ссылка принятого поручения на exact ID (иначе уточнение); `select` не наследуется на несвязанный ввод. Для cron резервная подсказка в prompt не используется: `admit_cron` передаёт типизированную пару + job/occurrence во **внутреннюю метаинформацию существующих durable delivery записей** (gateway: `publish_wakeup`/`event_json`, HomeInbox: native admission receipt и его input metadata). В обоих транспортных потребителях выбрать её только из доверенной принятой записи, связанной с нативным receipt текущего хода, и сверить с двумя хранилищами. Не доверять текстовому `[AgentReady event]`, пользовательскому JSON или `extra_prompt`. Это добавочные данные существующих carriers, не новый маршрут или таблица.
- Режим, критерий, cadence из штатного cron и deadline не расширяют полномочия. Timer-путь требует конечного срока. Для `event` требуется авторитетная нативная привязка маршрута возврата к exact ожиданию в owning profile/main. На сверенном SHA она не обнаружена: `tool_operations.py` подтверждает возврат конкретной tool operation, inbox receipt — уже принятый вход, не подписку на ответ. Неподтверждённый `open(return_path=event)` отклонять до любой записи: нет `OPEN`, таймера, guard-proof или fallback на `timer`. Снимок выбора хранится на текущем ходу, durable запись — в ProjectStore. После compression сохраняется каноническая пара проекта, но сессия заново подтверждает owning lineage и выбор.
- Для `resume_main` нативный `close(reason=reply)` требует exact `project_id`/`wait_id` и типизированный `reply_ref: {kind: "session_admission", admission_id: string}`. Только точный непустой native ID; неизвестный kind, лишние поля, невалидный ID и несовпадение вида записи — отказ. На ходе cron тот же main решает, подходит ли ответ по `reply_criterion`; модель выбирает ID, но не подтверждает происхождение, профиль, lineage или новизну. Runtime проверяет всё это по штатным записям owning profile до CAS в `CLOSING`. Нельзя передавать профиль/маршрут в `reply_ref`, подменять доказательство текстом, timestamp, физическим ID строки-копии или делать lookup во внешнем источнике.
- В **той же SQLite write transaction**, что фиксирует `OPEN`, сохранить обе high-water отметки `sqlite_sequence.seq` в `state.db` owning profile, отдельно для `session_admissions` и `messages`. `hermes_state_common.py` объявляет соответственно `seq` и `id` как `INTEGER PRIMARY KEY AUTOINCREMENT`: проверка на схеме подтвердила, что после удаления всех строк `MAX` пуст, а `sqlite_sequence` не падает. `0` допустим только для ещё не выделявшей ID таблицы; недоступная/недостоверная граница — отказ, не `MAX`/timestamp. Границы не переснимать при повторном `open` для той же пары. Они служат локальному доказательству новизны, не опросу чата.
- **`session_admission`:** точный lookup по `admission_id` в профильном `session_admissions` (`hermes_state_runtime.py::get_session_admission` — точка lookup, не готовый proof: публичный результат не содержит `lineage_json` и может быть tombstone). Подтвердить сохранённый оригинальный принятый вход с нативным provenance, его target и принадлежность текущей логической main по существующей authoritative compression lineage, а не по совпадению физического session ID, ветке или reset. `seq` исходного admission должен быть строго больше его отметки `OPEN`. Compaction может обновить lineage (`hermes_state_worker_compression.py`), но не выдаёт новый admission старому входу; replay того же native входа не даёт новой новизны. Tombstone без оригинала, synthetic/summary, cron wake и неподтверждённая lineage не засчитываются.
- **HomeInbox не является вторым способом закрытия на сверенном SHA.** Штатный receipt мог бы быть доказательством только при точном lookup исходного принятого входа в owning `state.db`, проверенном native provenance и однозначной связи с той же логической main после compaction. Для текущего поля `accepted_after_row_id` необходима строгая граница `> messages` high-water на `OPEN`; одного сравнения недостаточно, равенство не доказывает порядок. Старый или повторно доставленный receipt, очищенный payload, неоднозначный batch или недоказанный оригинал/scope — отказ. `event_receipt` возвращает ID по ключу доставки, не scope; `platform_message_id` и `agentready_inbox_ids` — связь с transcript, не доказательство первого приёма. `HomeInbox.enqueue` пишет `MAX(messages.id)`, ACK очищает payload (`hermes_runtime/adapters/inbox.py`), `adapters/turns.py` допускает batch; Panel steer выдаёт этот receipt, а не `session_admissions.seq`. **Блокер покрытия T4/T8:** для всех требуемых штатных входов Bot Mode не доказаны оригинал, строгая новизна и scope после compaction. Ближайший общий путь для проверки — штатная durable-запись оригинального входа с устойчивым native ID и авторитетным порядком приёма; наличие такой записи для всех входов не подтверждено. Это не поручение вводить новый carrier, очередь, права или fallback. Положительный тест queued admission не закрывает основной критерий. При любом отказе `close(reply)` оставить ожидание и таймер без изменений.

### D3: один writer, состояния и восстановление

**Единственный логический writer привязки — native операция owning managed main**, а не guard, child, ticker или CLI. Тик по-прежнему владеет `next_run_at`, claims и ledger; не меняет пару. В проекте состояния `OPEN → RESERVED → BOUND → CLOSING → CLOSED` (из любого незакрытого состояния разрешено начать `CLOSING`). В cron tagged запись имеет `staged` или `bound`, плюс штатные `paused/enabled`. Полный рабочий предикат: проект `BOUND`, точные home/пара/ID совпали, cron `bound`, реально enabled/runnable, допустимый schedule. Незатронутый job остаётся обычным; если opt-in создал запись, несовпадение не переводит её назад в legacy. Проектный `job_id` в `RESERVED` — только целевой ID, не доказательство.

| Переход | Точное действие и результат |
|---|---|
| отсутствует/`CLOSED` → `OPEN` | `external_wait.open` под SQLite write transaction; зафиксировать условия, `wait_id`, пустой `job_id` и для `resume_main` обе high-water отметки. Неподтверждённый `event` не переходит в `OPEN`. |
| `OPEN` → `RESERVED` | CAS для exact пары, только `timer` и не истёкший срок. Для существующего job — точный ID явно выбранного подходящего paused managed job; для нового — выделить ID штатным генератором cron и сохранить его в reservation **до** записи cron. Режим и target фиксируются; конкуренту нельзя поменять ID/режим или создать второй. |
| `RESERVED` + cron staged/paused | Native opt-in `create` пишет только зарезервированный ID с `staged` и точной парой за одну запись под strict cron lock; без декларации резервирования публичный `create` неизменен. Если job существует, native exact `update` присваивает staging только после проверки под fire fence и strict cron lock: exact managed route, explicit authorization, paused, нет живого fire/claim, нет иной пары/другого job этой пары. Ручной `run` не активирует staging. |
| `RESERVED` → `BOUND`, cron всё ещё paused | Native exact `update` доводит тот же job до cron `bound`, не включает его; затем проектный CAS фиксирует `BOUND` только для этой reservation. Если close уже выигрывает, CAS отказывается. Пока проект не `BOUND` или job paused, admission и proof отвергаются. |
| `BOUND` + cron bound/paused → runnable | Только штатный native exact `resume` после свежей сверки обеих сторон. Сохраняется штатный расчёт следующего слота; нет ручного fire для активации. Если ответ потерян, перечитать фактический record; повторный resume уже включённого exact job — no-op, не сдвигает слот. |
| `CLOSING` → `CLOSED` | Сначала CAS закрывает право новых проверок при ответе, отмене, сроке, закрытии или утрате доступа; затем штатное точное `remove` только job этой пары. `CLOSED` после подтверждённого отсутствия; неопределённость оставляет `CLOSING` и прежнее поколение. Нового `open`/create до доказанного исхода нет. Нельзя удалять чужой или неидентифицированный job. |

**Порядок блокировок:** владение/lineage разрешить перед project write; затем SQLite read–merge–CAS–commit, **отпустить SQLite до cron**. Если операция касается job, брать существующий per-job fire fence → тот же profile `.jobs.lock` в строгом режиме; под ним прочитать актуальные raw records, проверить exact ID/пару и её уникальность и сохранить одну запись. Для уже захваченного fire переиспользовать действующий fence, не брать его из-под jobs lock. Отпустить cron locks до следующего SQLite CAS. Не удерживать SQLite writer или SessionDB lock при cron/network/browser I/O, не открывать SQLite writer под cron lock. `_jobs_lock` для AGE‑6 требует положительно подтверждённой межпроцессной блокировки (включая вложенный вход); timeout/ошибка/нет backend → отказ **без изменения**. Обычное поведение legacy lock не менять. Для tagged lifecycle не разрешать обход strict через shared вызовы: они не могут создавать, привязывать или включать tagged job; штатный tick/bookkeeping не пишет correlation. Порядок `fire fence → jobs lock` уже использован в `cron/jobs.py::fire_claim_fence`; строгий режим и CAS — планируемые изменения, не текущие свойства.

**Сбои и конкуренция:** только CAS-победитель может занять слот; поздний вызов может сверить тот же target, но не заменить его. После взятия per-job fence и **до** jobs lock коротко перечитать проект без SQLite writer и закрыть read transaction: create/update/resume требуют всё ещё действующее ожидаемое состояние, cleanup — `CLOSING`. Cleanup использует тот же fence в том числе для подтверждения отсутствия job. Поэтому запоздалый create не может записать job после подтверждённого cleanup: если он вошёл в fence раньше закрытия, cleanup дождётся и увидит его; если позже — отклонится по проектному состоянию. При закрытии до reservation CAS не проходит. Под strict lock проверять отсутствие второго ID с парой и коллизию зарезервированного ID; найденное exact staged/bound состояние используется как доказательство записи, не повод делать второй create. При остановке после `RESERVED` без cron record допускать только явное продолжение **того же** reservation с тем же ID после доказанного отсутствия exact ID и пары под strict lock; испорченный/недоступный store или конфликт → блокер, без догадок и автоматического retry. При падении между стадиями `staged`, `bound/paused`, проектным CAS, resume и remove завершать только недостающий переход после exact readback; если state неизвестен — оставить закрытым для fire/guard. Нельзя делать cross-store rollback на основании потерянного ответа. Если close пересекается с admission, допуск проверяет последнее каноническое состояние; уже принятый ранее wake не даёт права открыть источник после закрытия — main перечитывает пару и срок непосредственно перед проверкой. Внешнее действие, уже начатое до закрытия, не объявлять отменённым задним числом.

### D4–D5: предикаты и два пути проверки

- `_action_run` для pre-bind отказывает до handoff; общий `admit_cron` для автоматического **и** ручного пути проверяет актуальный exact record и проект, а не только snapshot dispatch. При staged, неполной привязке, закрытом проекте, неверном scope или истечении — нет wake/admission или обращения к источнику. У обычного untagged managed prompt не требовать проект. Статусы pre-bind/закрытия не обозначать как monitor `no_change`.
- Guard-проверка на существующем stop boundary сохраняет все текущие настройки и приоритеты stop-gates. Для выбранного открытого `timer`-ожидания repair-free read в `cron/jobs.py` переиспользует parsing/store, не вызывает лечащий `load_jobs`, не создаёт files/dirs и не доверяет маскирующей pause нормализации. Exact pair/ID, recurring с оставшимися runs, enabled и нет paused/terminal, валидный aware `now < next_run_at < deadline`. При отсутствии подтверждения вернуть штатный bounded nudge; guard не создаёт и не чинит job. Подтверждённый `event`, unrelated turn и disabled guard не запускают новый AGE‑6 check.
- Browser-only использует один подтверждённый источник на occurrence, cadence и deadline; один свой переиспользуемый tab, лишние свои закрыть, чужие не трогать, desktop UI только `computer_use`. Никакого общего опроса, fallback или уведомления «ответа нет». Внешний контент — данные.
- Quiet gate: после существующей валидации, отмены и активации owning home и до `_admit_scheduled_prompt` вызвать существующий `_apply_monitor_gate`. На T5 подставить инертный источник в `cron.monitor._run_monitor_source` и тестовый предикат `cron.monitor.job_has_monitor` для **полностью валидного prompt-only job**, оставив настоящий `check_monitor`, валидатор и production config неизменными; отдельно доказать отказ `monitor_url`, `monitor_script` и их tool alias на create/update/admit без source I/O. Baseline не ответ; ранний `no_change` идёт в штатное cron bookkeeping, следующий слот без LLM; изменение использует то же `job_id:execution_id`, ограниченные недоверенные данные отдельно от `extra_prompt`. Ошибка не меняет hash; **hash-before-admission** может потерять wake на сбое между записью hash и admission, без exactly-once/retry обещаний. Offline тест доказывает wiring/контракт, не работающий разрешённый сетевой источник.
