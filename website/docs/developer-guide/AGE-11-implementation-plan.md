# AGE-11 — Gemini через официальный `agy -p`

**Согласованный вердикт Spec: GO для полной разработки и интеграционных проверок без сети и учётных данных; live capability закрыта по умолчанию и не регистрируется на неподтверждённом рантайме.** Это замена прежнего NO-GO, а не разрешение на живой вход, вызов модели, смену тарифа, QA rollout или выпуск. ## 3. Модельный адаптер и границы процесса

**Стык кода.** `providers/base.py:326–349`; `providers/__init__.py:122,192,691+` (registry/discovery); `hermes_cli/runtime_provider.py:1038–1184`, `runtime_provider_backends.py:252–278`, `hermes_cli/auth.py:2128+,2318–2339` (учитывать пользовательский command/base URL у других external-process providers, не наследовать их для этого ID); `agent/agent_runtime_helpers.py:1829–1858,1963–1979` (ошибка custom create сегодня может перейти в встроенный HTTP-клиент); `agent/auxiliary_client.py:5243–5254,5349+` (не допускать auxiliary discovery/implicit delegation). Поставить адаптер как явный provider module; не auto-register его bundled discovery до trusted admission. Известный canonical ID обрабатывать fail-closed **до** generic explicit URL/key, custom, alias, auto, resolver fallback и HTTP construction. Предусмотреть typed `unavailable/auth_required/auth_expired/transport/protocol/containment` со статическими сообщениями; не проглатывать ошибку create для этого provider. В CLI/Gateway/TUI путь разрешения и `agent/turn_api_error.py:257–398`/`agent/turn_recovery.py` не запускают resolution/turn fallback, rotate, rebuild с новым child или повтор после spawn; проигнорировать даже старые `fallback_providers` на этом маршруте. Отсутствие бинаря — `unavailable`, не HTTP. Явный ручной выбор другого существующего источника — отдельная операция.

**Запрос и limits.** Один `argv`, без shell: absolute image-owned binary, фиксированный режим `--model <pinned catalog id> --output-format stream-json -p <text>`, + описанная политика запуска и `--print-timeout 120s`. Без `--json-schema`, `--input-format`, `--conversation`, `--continue`, и remote flags. Payload — UTF‑8 JSON-пакет с версией внутреннего формата, авторитетными системными инструкциями Hermes, неизменённым порядком подготовленных сообщений (текущий пользовательский запрос уже последняя запись), и снимком фактически предложенного Hermes tool catalog. Роли и JSON-данные отделены структурно; tool output/пользовательский текст не могут добавлять поля пакета или команды; model-role priority этим не обеспечивается, поэтому runtime/validator авторитетны. Не передавать внутреннюю metadata, local credentials, login URL, сырые persistent rows, неявный base URL или сырые provenance поля. Допустимые части — текст и канонические tool calls/results; смешанные media blocks → `unsupported_input` до spawn. Не менять историю для укладки в лимит: штатная компрессия до построения снимка, затем локальный `input_too_large` без запуска. Лимит сериализованного prompt 96 KiB UTF‑8 (с запасом под Linux per-argument cap); без NUL; `E2BIG` локальная ошибка. Нельзя раскрывать argv в логах; процессное пространство в live изоляции не должно делать prompt наблюдаемым соседнему профилю через `/proc`, debug или телеметрию.

**Поток.** Ограничения v1: 4 MiB stdout/4096 NDJSON lines, 256 KiB одна строка, 64 KiB bounded diagnostic stderr, 128 KiB decoded `response`, 32 KiB `arguments`, глубина JSON ≤32; лимит байтов и глубины проверять до дорогой обработки. Строгий UTF‑8; LF или CRLF, без BOM, пустых записей, незавершённой последней строки, неоднозначных/дублирующихся ключей на **всех уровнях обоих JSON**, NaN/Infinity/переполненных чисел и невалидных Unicode scalar. Один `init` первым для успешного запроса; затем только перечисленные безопасные `step_update` из официального примера (`user_input`, `agent_response`, `checkpoint`, без полей действий), согласованные conversation IDs там, где они представлены, один terminal `result`, EOF, exit 0. Не делать allow по префиксу: использовать фиксированные поля/типы pinned docs и инертные синтетические fixtures; Mac-наблюдения приняты из карточки, исходный поток Spec не архивировал. `result.status == SUCCESS` и `result.response` строка. `num_turns` — необязательная ограниченная диагностика, накопительный счётчик сессии: не требовать `== 1` и не выводить из него число subprocess или доказательство запрета нативных действий. `result.ERROR`, неожиданный/повторный `init/result`, bytes после terminal, конфликтующие идентификаторы, ненулевой rc, обрыв, soft deny, unexpected tool/action/MCP/hooks event → ошибка шага даже при parsable final. У non-success может не быть `init`: классифицировать как auth только по квалифицированному сигналу pinned версии, иначе общий provider error. Не читать `structured_output`, markdown fences, `text_delta`, first-object substring или stderr как ответ; `step_update` не показывать как чат-дельты.

**Внутренний ответ.** Ровно `{type:"final",answer:string}` (непустой после проверки whitespace; сохраняется исходный текст ответа) либо `{type:"tool_call",id:string,name:string,arguments:object}` с точным набором ключей; JSON object без текста до/после кроме JSON whitespace. `id` ASCII `[A-Za-z0-9_-]{1,64}`, без служебных префиксов native/bridge нормализации; имя только точное в каталоге запроса и в текущем runtime scope. Схема аргументов берётся из того же immutable источника, что ушёл в prompt; проверять типы/ranges/required/additional properties по схеме, без coercion, `$ref` никогда не загружается из сети. Для неизвестного/неподдерживаемого dialect, небезопасного ref или невалидной схемы не рекламировать этот инструмент и отклонять его имя; не подменять более широкой схемой. Переиспользовать поддерживаемый Core validator, если гарантирован в runtime image; на START `jsonschema 4.26.0` есть в `uv.lock` только транзитивно. Если такого Core API нет, явно объявить одну bounded зависимость `jsonschema` (`>=4.26,<5` в `pyproject.toml`; `hermes pm lock`) и проверить установку в runtime image; не писать частичный валидатор схем. Provider выдаёт одну обычную Hermes completion (`stop` + текст, либо `tool_calls` + singleton function с JSON args). Если нужен streaming interface, один согласованный chunk/finish **после** проверки EOF и exit; ничего не публиковать из промежуточных событий.

**Жизненный цикл.** Request-local pipes/deadline/cancel handle; stdin закрыт для print, ни один PID/CLI conversation не переиспользуется. Concurrent drain stdout/stderr с буферами по указанным максимумам. Внешний monotonic hard deadline 125s от spawn, timeout/overflow/неразрешённое событие/cancel → отказаться от публикации, закрыть вход, TERM process group / затем KILL не позже 2s grace и reap под supervisor; тестировать дочерний процесс и FD leak, не только один PID. `cancel/close` идемпотентны; interrupt через текущие callbacks Hermes, принятый terminal не выигрывает гонку с отменой до native persist/dispatch. Автоматический retry только локальной подготовки **до** spawn (без I/O в Google); никакого автоматического повторного запроса при неоднозначном исходе, ошибке модели/auth, повторном ID или timeout. Следующий новый шаг после устойчивого результата — обычный loop, не retry; повторная реплика пользователя — новый ход. Сырые prompt/stdout/stderr, argv, auth paths и URL не попадают в логи, ошибки, traces или process diagnostics; отмечать redacted код стадии, elapsed/bytes и неприватные идентификаторы теста. Не глушить отказ: `protocol_error`/`containment_violation` видимы и не маскируются `final`.

## 4. Единственное исполнение и история Hermes

1. Stable turn owner даёт `home + logical session key/id + turn ID` (`agent/turn_context.py:576–601`, gateway owner scope); перед native dispatch проверять предложение до `agent/turn_tool_validation.py:89–103`, где обычный код *переименовывает* duplicate IDs. Добавить узкую проверку в `agent/turn_tool_round.py` для этого canonical provider: взять raw ID из уже валидированного singleton и полный in-turn set владельца (сохраняется через compression/adoption/rebuild), не опираться на урезанный API prompt. Любое совпадение ID в этом ходе, даже при равных args, либо коллизия с каноническим ID в поданной истории → `duplicate_tool_call`, без uniquify, добавления новой заявки и dispatch. Сравнивать также нормализатор Hermes; допустимые IDs должны сохраниться без изменения end-to-end, модель в prompt инструктируется выдавать новый ID, не занятый предыдущими строками. Две заявки на одну операцию, но с разными ID — штатные вызовы под обычными guardrails, не глобальная exactly-once гарантия произвольных эффектов.
2. Единственный producer durable assistant call — `run_tool_round` и `_flush_messages_to_session_db` **до** UI и `_execute_tool_calls` (`agent/turn_tool_round.py:110–177`; `agent/session_persistence.py:288+,467–511`; таблица `hermes_state_messages.py:31+`). Для этой ветви требовать `flush is True` после возврата из штатной SQLite транзакции (отдельное соединение для readback в тесте); `None`/disabled/unavailable, потеря или непрочитанная owner generation не считаются успехом. In-flight ID резервируется существующим единственным владельцем хода до flush; при неоднозначном flush dispatch запрещён, ID не повторяется. Не добавлять dispatch в provider и не полагаться на diagnostic `note_turn_start` как lock. Duplicate и orphan tail при recovery проверяются по каноническим строкам/turn lineage в актуальном owner — никакого replay старого assistant-call как новой работы. В тесте restart/cancel закрывает старого owner через штатный lifecycle и reopen readback, не полагается на process-local set после смерти worker.
3. Реальный execution seam — `run_agent.py:1304+` → singleton segment в `agent/tool_executor.py:1654–1698`; там штатные middleware/approval/tool scope, inline/context tools или `model_tools.handle_function_call` с теми же owner IDs (`tool_executor.py:1442–1511`). Provider не предоставляет альтернативного вызова, не запускает действия из текста результата. Перед исполнением native dispatch применяет штатную отмену, toolset/scope и validators; если каталог изменился после отправки, вызов больше не разрешён. Такой отказ/отмена идут через существующий безопасный терминальный результат; не следуют HTTP fallback или auto-approve.
4. Canonical tool result формируется `agent/tool_dispatch_helpers.py:448–480`, публикуется и flush-ится `tool_executor.py:202+,1593+` (deferred receipt `agent/tool_operation_lifecycle.py:134–145`). Только после успешного flush результата, без halt/cancel/scope loss, следующий запрос использует `role:tool`, тот же `tool_call_id` и канонический content; для незавершённой deferred операции сохраняются штатная квитанция и управление Hermes — `agy` не ждёт или опрашивает её. Если dispatch начался, но результат потерян/flush отказал/worker упал, статус неизвестного эффекта закрывается штатным orphan/interrupt path (`agent/turn_finalizer.py:258+,650+`), **не** повторяется автоматически. Без журналируемой внешней транзакции это at-most-once admission на идентификатор в ходе, а не обещание exactly-once в чужом сервисе. Новому owner начинать работу только после штатного release/recovery предыдущего хода; если canonical tail нельзя восстановить, остановить Gemini, не подставлять синтетический результат успешного выполнения.
5. `final` идёт в обычный finalizer/Panel chat текущей сессии; Dev readback SQLite после reopen проверяет ровно один assistant и один tool row на каждый ID и итоговую assistant row **до** зачёта QA. History хранится Hermes: нативные project/session state/логи `agy` не читаются для replay; неизвестные native записи считаются риском, writable scratch уничтожается, а допустимые persistent auth writes ограничены выделенным store (см. ниже).

## 5. Pre-prompt допуск, хранение и истечение входа

**Два разных отказа.** До создания child и передачи чувствительных argv/login попытки `admit(profile, operation)` получает из доверенного runtime (не config пользователя, не параметров Panel, не произвольного PATH) immutable launcher policy + факт активного профиля. Для live должно одновременно совпасть: image digest/source SHA, pin бинаря и digest правил/обёртки, подтверждённая OS isolation на этом runtime, назначение auth namespace, и явный разрешённый неплатный QA entitlement для этой среды. Офлайн production-ветка `admit` возвращает `unavailable`; fixture инъецируется в test constructor только в тестовом процессе, без production switch, внешнего URL или fake credentials в релизе. После старта неожиданное событие о нативном действии означает containment/policy failure и **отказ всего шага до Hermes dispatch** с зачисткой; это детектор и аварийная остановка, не защита от уже совершённого эффекта. На следующем запросе подозрительный runtime не переходит обратно в доступный автоматически: отозвать допуск и перевалидировать образ/политику.

**Supported policy + настоящая OS isolation.** Явные default agent mode (`agentMode: ""`), `toolPermission: strict`, документированные `permissions.deny` для всех доступных небезопасных классов операций в qualified manifest, включая чтение, запись, команды, сеть/MCP по опубликованным action types; отдельный чистый CWD, `--disable-slash-commands`, `useG1Credits: false`; никакого `--dangerously-skip-permissions`. Фиксированный image-owned agent manifest (если входит в квалифицированный профиль), `commandExecutionPolicy: "off"`, `tools: []`, `skills: []`, `inheritMcp: false`, `inheritCustomizations: false` — только defense in depth. Нельзя поставить fail-open `PreToolUse` в качестве единственной границы. **До exec/первого prompt** доверенный launcher должен обеспечить: отдельную identity/PID/tmp/state и ограниченный filesystem view со read-only image/settings, пустой рабочей областью, без tenant workspace/profile volume/agent config/plugin & hook sources/launcher sockets, соседних процессов, service-account/cloud metadata, host D-Bus/keyring или inherited credentials; только выделенный этому employee auth store нужного generation. Закрыть запуск/доступ к произвольным процессам, MCP startup, native plugin sources, remote control и нецелевой network egress, не открывать неограниченные сеть или ключницы для inference. Изоляция должна ограничить и внутрипроцессные actions (`manage_task`, `send_message`): если нельзя исключить старт, состояние, передачу/пробуждение внутри sandbox или через разрешённый Google endpoint (а не просто вред хосту), доказательства недостаточны. Не считать UID, пустой HOME, `--sandbox`, `init`, zero calls, post-hoc kill, либо file deny достаточными по отдельности. Off-path startup и fail-open hooks/MCP должны быть недостижимы, не просто отсутствовать в успешной трассе.

**Критерий выбора и размещение.** Shared Hermes Pod держит все профили, а employee Desktop/tool sandbox монтирует пользовательские данные и имеет иной lifecycle: ни один не принимается автоматически как граница `agy`. Для QA-дельты Dev переиспользует узкий стык `hermes_runtime/standalone/agy_runtime.py::admit` и существующую поставку `Dockerfile.agentready`. `deploy/kubernetes/render_shared.py:37–59,66–74` монтирует общий профильный root и управляющие сокеты; сеть ограничена на уровне pod, а не отдельного child. Employee Firecracker/terminal имеет другой жизненный цикл и доступ к employee workspace. Ни один путь не даёт AGE-11 per-generation process/keyring scope. Нет подходящей enforced границы — до exec отказ, без общей Popen, расширения привилегий, env/config-флага или нового сервиса в этой дельте. Реализуемая независимо часть: фиксированные login/probe, строгий readback, защита смены поколения и упаковка. Требуемый изолирующий launcher остаётся работой команды, а не ожиданием ссылки или стороннего готового артефакта.

**Auth owner/storage.** Profile authority `gateway/run_runtime.py:465–482` → `hermes_runtime/standalone/panel.py:275–318,342–356` под `owner_scope`, фиксированный home из registry, `Subscriptions(home, auth)` — не RPC payload. Credentials пишет/читает только официальный CLI в изолированном store, адресованном доверенным launcher по `(environment/profile owner, auth generation)`; контейнер login/probe/print одного поколения видит один и тот же store (тот же постоянный backing store, локальный Secret Service/keyring только этой identity или доказанный штатный native fallback). Директория metadata `subscriptions/agy` в профиле — mode `0700`, record mode `0600`, atomic generation transition, без секретов/endpoint, без symlinks/shared keyring/copy из launch profile. Не полагаемся на `HERMES_HOME`/`HOME`/`chmod` как изоляцию UID/DBus; stock documented auth использует OS keyring и cache. `tools/environments/local.py:394–435` помогает scoped env, но `agy` получает новый минимальный allowlist, а не унаследованный `os.environ`. В config.yaml — только публичный provider/model, не путь приватного backend или token. Резолвер не принимает credential handles из UI/логов/restore. Pending generation не используется inference; успешный A probe подтверждает физически тот же store, затем atomic метаданные выбирают generation, а не копируют/читают token. При падении до promotion generation остаётся недопущенным; доверенный cleanup стирает только вынесенный приватный scratch/непривязанное поколение, не существующие auth соседей. On restart pending attempt не восстанавливается, действующая привязка проверяется по durable owner + generation, policy и native status, не по наличию каталога.

**Lifecycle входа через штатный Panel.** Переиспользовать форму кода и route, а не реализацию `ClaudeLogin` без изменения: `panel_claude_login.py:16–97` — пример `Popen`/пула/reap, `panel_subscriptions.py:26–74,85–170,224–264` — authority и redaction. `start` допускается только владельцу configured environment, одна действующая попытка на `(home,provider)`, новый `sessionId` привязан к authenticated viewer/connector generation, PID и staged auth generation. Только фиксированный `agy acp --login` без inference; pipe non-TTY, ограничение до 15 min, bounded drain, cancel/owner retirement — TERM/KILL/reap той же группы. `start/poll` отдают URL только в защищённый связанный ответ: HTTPS, точный Google OAuth host/path, документированный callback (валидировать schema/host/path целиком, no credentials или fragment, не переписывать state/challenge). Предел URL 4096 UTF‑8 bytes, одна валидная ссылка из bounded pipe. URL/код не попадают в логи (включая native CLI log files и debug), transcript, telemetry, browser storage или fallback response; проверять native диагностику в изолированном scratch и не допускать live, если секреты выводятся/записываются. Код не сохраняется персистентно. `code` только защищённый штатный UI, без авто-retry отправки; один ASCII printable non-whitespace value 1–4096 bytes, отвергнуть CR/LF/пустой/многострочный **до** каких-либо trim/нормализации; один `code + LF` в stdin того же PID, потом закрыть pipe. Повторный `code` не write и не restart, UI очищает поле при отправке/смене профиля/unmount; на потере ACK только `poll`, не отправить тот же code повторно. Relay повторно проверяет тот же user/environment и entitlement `canConfigure && !support` перед изменяющими RPC Gemini; `poll` не раздаёт финальную квитанцию чужому или уже отменённому sessionId. Preview URL/`sessionId` в volatile memory до terminal/TTL; TTL и cancellation не хранят одобрение от невалидного потомка. Ни privileged chatter, ни assistant tool не видят код.

**Readback, expiry, revoke.** `submitted` = принята строка, не `connected`. `invalid_grant` при исходном login → `error_invalid_code`, не истечение действующей привязки. Exit 0 login → `verifying`, store A остаётся staging. Тот же host authority, который запустил protected login, запускает **новый** `agy -p` (иной PID, pinned модель, фиксированный короткий ответ), сверив `(owner, auth generation, backing store/keyring namespace, launcher policy)` **до exec**. Этот store должен быть изолирован и иметь ровно одну штатно выбранную авторизацию, без чтения токенов и других аккаунтов; отдельный гипотетический vendor identity API не требуется (`telegram:1114`). Строгий `result.response`, SUCCESS, EOF/exit и ожидаемый ответ подтверждают использование уже привязанного store, не identity по словам модели. При отмене, недоступном/заменённом authority либо проваленном результате promotion нет; только durable CAS того же generation даёт `approved/connected`. Проверить независимый пустой B, который не наследует A; никакого другого аккаунта/тарифа в этой дельте. Синтетический тест store — fixture, не результат Google.

Для ранее A-connected revoke/expiry authoritative event: штатный native signal квалифицированного CLI об истёкшем/отозванном доступе при новом print с тем же поколением (не произвольный `result.ERROR`, сеть или `invalid_grant` входа). Прекратить приём новых запросов A, инвалидировать/обновить status только той generation под lock, вернуть в chat сообщение о переподключении без авто-логина, rotation или смены провайдера; B не меняется. Отдельно `disconnect`: после явного выбора другого источника и доказанного apply снять локальный binding, отозвать допуск для поколения, дождаться остановки его inference/login и подтвердить, что новый print больше не получает эту привязку. Native `/logout` документирован как интерактивный вызов CLI; не выдавать это за поддерживаемый noninteractive API. Квалификация живого удаления/отзыва требует доказанного officially supported действия для этой изолированной identity и native readback; без него не объявлять Google revoke из локальной очистки. Cancel/retire не отменяют случайно одобренную active generation: CAS на attempt/generation, process token и проверка owner перед финальным сохранением. B keyring и чужой login не трогаются.

**Тип входа ≠ квота.** Это Google account / официальный CLI OAuth/PKCE с native credential cache, а не проектный API key, ADC или browser OAuth Hermes. Google FAQ не поддерживает сторонних агентов на consumer планах, поэтому доступную личную Google AI Pro/Ultra квоту не заявляем. `useG1Credits:false` обязателен и не доказывает отсутствие billing. Решение о допустимости указанного активного аккаунта принято поправкой от 26 ноября; повторного согласования или замены аккаунта/тарифа не нужно. Решение не является доказательством выполнения стендового прогона или основаниями для автодопуска в образе.

На Gemini `code` использовать новый строгий тип без изменения Claude parsing. На `select` Gemini запрещает `managedFallback:true`, и effective Gemini runtime не применяет даже заранее существовавшие fallback entries; сохраняет `model.provider/default` и native revision атомарно, без ключа, URL или добавления нового config surface. Валидный managed route сохраняется штатным механизмом для явного возврата; другие провайдеры сохраняют их поведение. В managed main `hermes_runtime/adapters/main_model.py:9–48` → `gateway/run_turn_runner.py:1209–1210` → `gateway/run_turn_prepare.py:119+` после durable `_RECEIPT` очищает override/cache и на следующем ходу выбирает scope; `saved/deferred` подтверждает только запись. Inactive/foreign/stale revision не меняет другой диалог. Readback обоих путей — совпадают `(profile, logical session, model-selection revision/provider/model, auth generation)` между записью и фактическим новым native request attestation; ошибка apply показывает «сохранено, не применено», retry apply перечитывает актуальный desired state, а не запускает модель повторно. Новый native request receipt подтверждает выбор, не право billing.
- **Карта писателей.** Штатные writers `panel_subscriptions.py::_write`, `hermes_cli/config.py::_write_config_state/atomic_config_replace/save_config/set_config_value/unset`, `hermes_cli/auth.py::_update_config_for_provider`, slash/config/API writers, `gateway/session.py::set_model_override` из `gateway/slash_commands_model.py`, TUI `config.set` и фоновые snapshot/rebase workers могут сохранять настройки/overrides; provisioning `AgentReady/deploy/kubernetes/{provision_profile_job,provisioner,shared_profiles}.py` создаёт/восстанавливает каталог и initial config. `hermes_cli/profiles.py` clone/export/import (`1267+,2138–2292`) и универсальные профайл backups/restore могут копировать весь home, включая ранее неизвестный каталог. - **Снятие/rollback.** Owner вправе явно выбрать ровно ранее валидный источник через `select`, затем `disconnect` Gemini. До сдачи live gate обязателен проверенный reversible rollback: закрыть admission выдачи новых запросов и availability, дождаться bounded завершения/reap по generation, вернуть сохранённый исходный маршрут проставив новую revision с проверенным actual runtime readback или остановить затронутый профиль до замены образа; не переписывать весь config, историю, другие OAuth данные. Старый образ может интерпретировать неизвестный provider как иной default — **не откатывать образ с ещё выбранным Gemini**. Если конфиг/квитанцию прочитать нельзя, прекратить выдачу работы этому профилю, не возобновлять на старой версии и не считать image rollback data rollback. Смешанные версии: feature-off и registration absent до подтверждённой пары; immutable policy требует exact version; при замене shared runtime stale generations недействительны. Остаточный private auth store не читается старым/другим владельцем; удаление/remote revoke подтверждается отдельно. Offline результат должен пройти regression Claude/OpenAI/managed.

**Dev вход:** согласованный docs-only SHA и точные два START; offline implementation + ограждения, все шаги 1–5. Не включать live capability ради smoke. **Независимый Review:** полный diff обеих веток на exact candidate SHAs; пройти чеклист и тесты с фактическим `.db` readback, отрицательными control cases, mode/owner state и immutable packaging. K2/K7 live proof может остаться открытым после успешного review offline результата, но не может быть отмечен как QA PASS.

**QA вход:** решения по механизму и указанному аккаунту приняты постановщиком; не возвращать их на повторное согласование. QA-кандидат требует фактически подключённого launcher в exact образе и сохранения всех pre-exec гарантий §5, а не одной финальной метки. Без пригодной границы `admit` остаётся закрытым и выкладка инертной пары для проверки Gemini не выполняется. После независимого review и включения допуска только в согласованном тестовом scope, штатный операторский QA проверяет поставку, OAuth compatibility и A/B; это не глобальная регистрация для сотрудников.

**QA на стенде** после независимого Review и резерва: `test.agent-see.ai`, отдельно approve точные `panel_sha`/`hermes_sha` из existing draft PR heads; сверить build source label, published image IDs, реально запущенные digests, CLI/policy и environment IDs до/после прогона. Оркестратор использует trusted image-only workflow только при совместимости с existing test topology; при новых требованиям namespace/provisioner это отдельное согласование, не privileged workaround. Full QA проходит K1–K8 через реальный Panel, от refresh/strict login до нормального ответа, multi-tool на инертных вложениях, reopened history, expiry, revoke и A/B. Ни test build, ни fixture, ни `result.SUCCESS` отдельно не зачёт. **Приёмка человеком** — отдельный шаг после отчёта QA на той же версии. Этот план не разрешает изменения PR/Linear со стороны Spec, deploy, production или merge.
