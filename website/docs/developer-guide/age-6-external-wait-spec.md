# AGE-6 — Возобновление поручения после внешнего ответа

Согласованная спецификация для [AGE-6](https://linear.app/agentseeai/issue/AGE-6) и [Hermes draft PR #2](https://github.com/agentready-tech/hermes-agent/pull/2). Код сверён на `d4a53c4d6742f866a5cd0e1e39731f3396a45d35`, база `codex/agentready-runtime` @ `5b22b8d6d08b842ef239308ab9a844a41d1c06fd`. SHA `e398a765a09080f738b3ab9459b1d98fb92b1c41` из ссылок Linear исторический. Цель — продолжить уже принятое поручение в том же основном чате, а не разработать интерфейс или фоновый браузерный сервис.

## Точка интеграции и границы допуска

`cron/scheduler.py:2573–2586` передаёт запуск в `cron/scheduler_authority.py:55–59`; результат managed `admit_cron` завершает этот маршрут до штатной подготовки промпта, где уже используется `_apply_monitor_gate` (`cron/scheduler.py:1577–1612,2279`). Переиспользование согласовано по п. 6 `AgentReady/AGENTS.md`: вызвать существующий gate из `hermes_runtime/standalone/events.py::admit_cron` после валидации, проверки отмены и активации владеющего профиля, но до `_admit_scheduled_prompt`. Сохранить штатные условия владения и scope cron/fire. Не менять нативный cron вне managed режима и обычный main prompt без monitor.

- `monitor_script` для managed main **остаётся закрыт** на create, update и admit. `validate_main_schedule` сейчас запрещает оба monitor-поля; не снимать запрет на `monitor_url` без доказательства, что фактический managed fetch подчинён существующим сетевым ограничениям и ограничениям владеющего профиля на всём пути запроса (включая перенаправления). Недопустимый или неподтверждённый источник не запрашивается. Нельзя заменять проверку запуском скрипта, raw fetch в обход ограничений или браузером.
- **Блокер URL-ветки на проверенном HEAD.** `cron/monitor.py:88–100` использует прямой `urllib.request.urlopen` с проверкой схемы HTTP(S), таймаутом и лимитом тела. Это не доказывает сетевой допуск; scope cron доказывает выбор home, но сам по себе не ограничивает сетевой запрос. Не подтверждено, что уже существующая политика охватывает именно этот fetch в managed cron. До подтверждения держать URL-вход закрытым и явно сообщать блокер; не добавлять новый сетевой механизм. Это блокирует включение `monitor_url` и приёмку реального URL-сценария, не остальные работы AGE-6.

## Обязательные критерии приёмки

1. **Тихая проверка.** Неизменный hash → штатный `no_change`/`[SILENT]` в cron-учёте без нового события inbox/wakeup, хода main, LLM-вызова и пользовательской доставки. У того же включённого recurring job остаётся будущий `next_run_at`: следующий слот сохраняет планировщик независимо от модели (`cron/scheduler_tick.py:62–72`); пересоздания нет. Ошибка источника — штатный cron failure, не `no_change` и не изменение; hash не обновлять, модель и браузер как fallback не запускать.
2. **Изменение и baseline.** Нативный первый замер сохраняет baseline; его штатное пробуждение помечено как baseline, не выдаётся за внешний ответ и само по себе не закрывает ожидание. Изменение после baseline допускает один ход на occurrence через `_admit_scheduled_prompt` (`events.py:78–94`) в том же логическом main-чате, независимо от поверхности создания таймера. Сохраняются текущий закреплённый gateway-маршрут или штатный HomeInbox при отсутствии закреплённого маршрута, ключ `job_id:execution_id` и дедупликация. Контекст monitor — ограниченные недоверенные данные, отдельно от пользовательского `extra_prompt`. Квитанция admission не подтверждает фактический ход или доставку ответа.
3. **Изоляция.** Отменённый до gate, невалидный или не принадлежащий профилю запуск не обращается к источнику и не будит main. Job, hash/snapshot, ledger, секреты и main route относятся только к owning home; совпадение ID или имени в другом профиле ничего не меняет. Не брать launch/default profile взамен.
4. **Ожидание.** `MAIN_SCHEDULE_INSTRUCTIONS` через существующий main-only suffix требует хранить в материалах проекта точный источник/переписку, критерий ожидаемого ответа, стабильные ID проекта и ожидания и точный `job_id`. Подтверждённый webhook/return path не дублируется таймером. Иначе main владеет **одним повторяющимся таймером на ожидание**: сначала найти и переиспользовать его через `cronjob_manage`, затем перечитать запись; удалить после ответа, закрытия, отмены или истечения срока. Не переписывать префикс действующего разговора или историю.
5. **Машиночитаемое доказательство.** Привязка — структурированная пара точных `project_id` и `wait_id` в существующей записи cron, сопоставляемая с канонической записью ожидающего поручения по точному `job_id`; без нового реестра или миграции. `agent/continuation_guard.py` при уже включённом guard в применимом managed main читает актуальную запись штатным cron API под owning home. Доказательство: точное совпадение пары и `job_id`, main route, повторяемость, job включён и не в terminal/paused, валидный timezone-aware `next_run_at` строго позже текущего времени. Не засчитывать имена, фрагменты промпта, вывод judge или старые квитанции. При установленном ожидании без доказательства вернуть ход существующим ограниченным механизмом: проверить/переиспользовать или поставить разрешённый таймер; если это невозможно, сообщить препятствие. Guard не ставит таймер сам. Не менять `enable`/default-off, предел продолжений или текущие исключения, в том числе для сабагентов, side agents и cron. Явная остановка сохраняется.
6. **Browser-only.** Если конкретный источник доступен только через браузер, recurring prompt возобновляет то же поручение в main, а не запускает отдельного агента. До создания таймера заданы точный разрешённый источник, критерий ответа, регулярность и конечный срок; за тик — одна ограниченная проверка. После срока источник не открывать; ответ, закрытие, отмена или потеря разрешённого доступа прекращают проверки. Использовать один свой рабочий tab, переиспользовать его, не трогать чужие; desktop UI — только `computer_use`. Никакого сканирования других переписок или широкого автономного polling. Отсутствие ответа не требует сообщения пользователю. Такой тик может использовать модель и не является quiet path из п. 1.

## Риск и неизменяемые границы

**Hash-before-admission:** `cron/monitor.py:126–186` сохраняет новый hash до admission. Если admission сорвётся после записи, следующий замер с тем же содержимым может подавить пробуждение: сохранённый hash не подтверждает доставку. Штатный отказ отражается в cron; не обещать exactly-once между этими этапами и не добавлять retry/fallback. Не добавлять очереди, таблицы, диспетчеры, browser worker, интерфейс, новый сервис или флаг. Сохранить существующий маршрут и профильный scope.

## План проверок

- Локально/CI на исходной и исправленной версиях: подтвердить регрессию и исправление через штатную точку входа managed cron в изолированном `HERMES_HOME`, с контролируемыми источником, часами и моделью. Через `scripts/run_tests.sh` (не bare `pytest`) проверить `tests/cron/test_monitor_kind.py`, `tests/cron/test_cron_profile_isolation.py`, `tests/hermes_runtime/` (main schedule, wake, route, policy, E2E) и `tests/agent/test_continuation_guard*.py`; затем `python scripts/check`. Не использовать действующие профили или live cron.
- Поведенческие сценарии: обычный main prompt и нативный cron; отказ скрипту и неподтверждённому URL на create/update/admit без fetch; для gate — baseline → повтор → изменение → ошибка/отмена. Доказательства quiet: `job_id`, `execution_id`, `no_change`, будущий persisted `next_run_at`, ноль inbox/LLM/доставок. Для изменения — одна запись на occurrence и фактический ход в том же main с gateway и со штатным HomeInbox; ошибку на границе hash/admission не считать состоявшейся доставкой. Настоящий URL разрешён только после доказательства действующей политики для этой ветки.
- Два изолированных профиля с совпадающими ID/именами и два проекта внутри одного home. Для guard проверить положительный случай с таймером из прошлого хода, затем чужую привязку, паузу/удаление, просроченный/невалидный `next_run_at`, недоступную запись, неподходящую сессию, default-off и исключения. Для browser-only на тестовом источнике проверить отсутствие совпадения, ответ и истечение срока: тот же проект/main, не более одного обхода за тик, снятие таймера и отсутствие действий за пределами разрешённого источника.
